00No command — the idea behind all of them.

The problem it solves

Suppose you ask: “how do merchants get their money faster?” The document that answers it says “settlement latency compresses working capital.” Not one word overlaps. Ordinary text search finds nothing.

Now search for a common word instead — payments — and you get four hundred hits, in no useful order. Too few results, then too many. That is the whole difficulty in one pair of examples.

The brain never trusts one method. It looks for your question in three completely different ways at the same time, then merges the three opinions into one ranking. Where one method is blind, another usually is not.

Everything else here is either preparing for that moment — indexing, embedding, graph building — or reacting to it: writing new notes back, checking the index has not gone stale.

01Applies to every command below.

What lives where

One rule governs the whole design: your markdown is the truth; everything the plugin builds is a disposable copy. Delete the working folder and you lose an afternoon of re-indexing — never a fact.

your-repo/                      ← the anchor: where you installed it.
│                               Trust weight 1.0.
├── docs/ notes/ memory/ …      your markdown — the source of truth
└── .company-brain/             everything derived, gitignored.
    │                           The only folder the plugin creates.
    ├── brain.db                one SQLite file holding every source:
    │                           text, keywords, vectors, entities,
    │                           relations, clusters
    ├── sources.json            the roots below, and their weights
    │                           ← the one file worth keeping
    └── .indexed                an empty marker file, timestamped

~/code/handbook/                ← added with /brain-source, weight 0.8
└── **/*.md                     read where it lies. Nothing is written here.

~/work/org-intel/content/       ← a subfolder is a valid root too
└── **/*.md                     read where it lies. Nothing is written here.

A single SQLite file holds everything: the chunks of text, the keyword index, the numeric vectors, the entity graph, the clusters. SQLite is just a database that is one ordinary file on disk — no server, no account, nothing running in the background.

Every repository you add lands in that same file. There is one index, one graph and one set of clusters, no matter how many sources feed them — which is what lets an answer cite your handbook and your meeting notes in the same breath. The extra repositories are read where they lie: an absolute path recorded in sources.json, walked on each index, never copied and never modified. A source root does not have to be a whole repository either; pointing at one folder inside a large one is normal.

sources.json is the exception to “disposable”. Its trust weight per source feeds directly into ranking — the anchor sits at 1.0, anything added later normally lower, so a less-trusted source has to be a distinctly better match to outrank a curated one.

Why this matters for the commands. /brain-index and /brain-enrich only ever write inside .company-brain/. The single command that writes real markdown is /brain-add, and it writes into the anchor. Adding a second repository does not make it a place notes get filed: capturing into one refuses to run unless you name the destination folder explicitly, because guessing a spot inside somebody else's corpus is exactly the wrong default.
02/brain-setupOnce, ever. Downloads about 2 GB.

Two Python environments, on purpose

The plugin installs two separate Python environments rather than one, and the reason is speed.

  • The server environment is tiny — a database driver, some maths, a graph library. It starts instantly, and it starts every time you open Claude Code.
  • The embedding environment is enormous — PyTorch and a multilingual model called bge-m3, roughly 2 GB. Loading it takes seconds.

If they were one environment, every session would pay those seconds. Instead the heavy one runs as a separate long-lived process that the server talks to over its input and output streams, one line of JSON at a time: here are some sentences → here are their vectors. The model loads once and stays warm.

This split has a useful consequence: if the embedding environment was never built or its download failed, nothing crashes. Search still runs on the other two signals and simply reports that the meaning-based one is unavailable.

The command builds the light environment, builds the heavy one, then sends it one throwaway sentence so the model downloads and warms up now rather than during your first real question. It reports the model name, the device it picked (Apple mps, Nvidia cuda, or plain cpu) and the vector size.

03/brain-indexreindexSeconds after the first run.

Cutting documents into index cards

A whole document is the wrong unit to retrieve. A 12,000-word strategy paper might answer your question in one paragraph; hand back the file and you have handed someone a haystack.

So each document is cut into chunks of about 240 words — think index cards. Every card remembers three things: which file it came from, the heading it sat under, and the line number it starts at. That last one is why a citation like strategy/uk.md:365 is possible at all.

What else it lifts out while reading

  • Metadata from YAML frontmatter, and also from the looser **Owner:** … style some corpora use instead. English and Spanish keys are both recognised.
  • A document date, from the frontmatter, the filename, or the first stretch of prose — in ISO, day-month-year and month-day-year forms. Dates in the future are skipped deliberately: those are deadlines, not the day the document was written.
  • Typed facts — lines like - owner:: Priya since:2026-03, stored as rows with a subject, a predicate, a value and optional since/until dates. Eleven predicates — role, employer, owner, status, location, stage, instrument, branch, lead, phase, tier — are functional, meaning they hold one value at a time, which is what makes contradictions detectable later.
  • Wiki-style links [[like this]], and a superseded flag when a document declares itself replaced.

Why re-indexing is nearly free

Every expensive result is filed under a content fingerprint — a short hash of the exact text. Documents are fingerprinted, and so is every individual chunk. A file whose fingerprint is unchanged is skipped entirely; a changed file is re-cut, but chunks whose own text did not move keep their existing vector and entity extraction, because those are stored against the chunk's fingerprint, not its position.

So fixing a typo on page 4 of a long document re-embeds one card, not the document, and certainly not the corpus. The first full build is genuinely slow. Every build after it is seconds.

At the end of every index run the plugin touches an empty file called .indexed. A hook that runs when Claude Code starts compares your markdown against that marker's timestamp and tells you how many files have moved ahead of the index — the same number the health strip at the top of this page shows. It reports; it never acts.
04/brain-indexBuilds all three lookups in one pass.

Three ways to find a card

Indexing does not build one lookup structure. It builds three, each blind in a different way. These three colours carry through the rest of this page.

The vectors, plainly

An embedding turns a passage into 1024 numbers — coordinates in a space where “nearby” means “similar in meaning”. Comparing two passages is a single multiplication, and the vectors are pre-normalised so that multiplication is the similarity score. Comparing your question against every card is one matrix operation, fast enough not to need any approximate index.

Teaching it who's who

Nothing so far knows that “Priya” is a person or that a company and a product are connected. Building that layer means reading every card and asking what it names — a job for a language model.

The clever part is who does the reading. Rather than calling a paid API, /brain-enrich uses subagents inside your own Claude Code session.

Two properties make this survivable on a large corpus. It is resumable: the queue is keyed by card fingerprint, so you can stop after any round and pick up later. And it is idempotent: a card whose text has not changed is never extracted twice, no matter how often you re-index.

Entities are stored under a normalised key, so Acme Corp., acme-corp and ACME resolve to one row, with every spelling kept as a searchable alias. Repeated evidence for the same relationship increases its weight rather than duplicating it.

Retrieval already works without any of this — keyword and meaning are live the moment /brain-index finishes. Enrichment adds the third signal and unlocks theme questions.
06merge_entitiesBetween enrichment and clustering.

Folding duplicates together

Extraction names things as the text spells them, so one company arrives as several rows: an abbreviation, its expansion, a legal name, and whatever a transcript made of someone's surname. Left alone this splits the graph — each fragment holds part of the connections, and looking one up shows you part of what is known.

The merge is deliberately conservative. It folds two entities together only when each side was independently declared an alias of the other. A one-directional claim is usually a part-of relationship, not a synonym — which is exactly what stops Acme Pay being swallowed by Acme.

Chains collapse in one pass, so a short name, a full name and a misspelling of it all land on the same row. The surviving row is the most-mentioned one — it carries the graph's mass — but it is displayed under the fullest spelling, and every variant stays a searchable alias, so retrieval is unaffected either way.

Run it with apply: false first to read the plan; the longest spelling is occasionally the garbled one.

07/brain-enrich --communitiesOnly once the extraction queue is empty.

Clusters, and what each is about

Some questions have no answer in any single passage. “What are our recurring risks?” is answered by a pattern spread across thirty documents that never mention each other.

  1. Partition the entity graph. An algorithm called Leiden finds groups of entities much more connected to each other than to the rest — the way friend groups emerge in a social network without anyone labelling them. It runs at two granularities, 0.6 and 1.2: a coarse pass giving few large clusters, a fine pass giving many small ones. Groups of fewer than three entities are dropped as noise.
  2. Summarise each cluster. A subagent is given one cluster's entities, the relationships among them, and real evidence passages, and writes a 5–8 word title, a 150–250 word summary and an importance rating out of ten — grounded strictly in the evidence supplied.
  3. Store the summary as a first-class object, embedded like any other text, so it can be searched on its own terms.

Re-summarising is incremental in the same way indexing is: each cluster is fingerprinted by its membership list, so after a re-index only the clusters whose membership actually moved need rewriting. These summaries are what the Communities tab lists.

08/brain-asksearch_evidenceThe moment everything else was preparing for.

Answering a question

Step 2, drawn: voting by position

This is reciprocal rank fusion, and it behaves like a ranked-choice election. Each method votes for a card with strength 1 / (60 + rank), and the votes are added.

Step 3, drawn: letting the graph vote

Score is released at the starting points and flows outward — a card passes credit to its document, its neighbours on the page, the entities it names, and the cards nearest it in meaning. Each round, 18% leaks back to the starting points, which is what keeps the walk anchored to your question instead of drifting to whatever is most connected overall. Seven rounds. This is personalised PageRank.

The final score, in proportion

Two more rules shape what you finally see: at most two cards from any one document, and never the same heading twice — so a long section cannot answer with two adjacent halves of itself.

What comes back is not an answer. It is ranked evidence — passages with a source, a path, a line, a date, a superseded flag and a score — plus a report of which signals were actually available. The reasoning stays with the model, and the answer standard the command enforces is: lead with the answer, cite path:line, keep stated evidence separate from inference, and surface conflicts rather than blending them.

mode changes the shape of the results: local concentrates on the best evidence, global forces the first five results to come from different areas of the corpus.

Questions no passage answers

Picking the right entry point matters more than phrasing the question well.

The command layer wraps this in a bounded loop: name the facets the answer needs, retrieve once, identify what is missing, then run at most two targeted follow-ups. Three passes maximum, on purpose — retrieval that recurses freely manufactures confidence it has not earned.

10/brain-addrememberThe only command that writes real markdown.

Putting knowledge back in

Everything so far reads. This writes — and it writes markdown into your repo, not a hidden row in a database. A note that existed only inside the index would be invisible to every other tool you own, and would vanish with the index.

/brain-add creates a dated, titled file in memory/inbox/ with frontmatter, tags, a confidence level and a provenance block, then immediately re-indexes, re-embeds and rebuilds the graph so the next search finds it.

Two things it is strict about

  • Confidence is recorded, not assumed. Every note is marked stated (you asserted it), observed (seen in a source), inferred (concluded) or draft. Nothing you did not actually say is filed as stated.
  • Typed facts are never invented. Facts use predicate:: value, or subject|predicate:: value when the fact is about something other than the note itself. They are only written when you actually stated them.

The note is auto-linked to entities it recognises, but only distinctive ones — aliases shorter than five characters and generic words like company or project are skipped, because linking everything to everything makes a hub that helps nobody.

Facts that go stale are closed, not deleted: add until: to the old assertion rather than removing it. History stays readable, and the maintenance report can then tell you when two open values contradict.

11/brain-dream/brain-sourcestatus

Keeping it honest

/brain-dream is a maintenance report. It reports and never edits — picking a winner silently is how a memory system starts lying. It looks for:

  • Contradictions — two open values for one functional predicate, each shown with its path:line. The fix is to close the older with until:.
  • Ageing facts — open functional assertions more than twelve months old.
  • Duplicate claims — the same fact stated in more than one file.
  • Superseded documents still being indexed, hubs that everything connects through, and documents no entity touches — usually a sign enrichment has not reached them.

/brain-source manages which repositories are read. add <path> <name> [weight] appends one; the weight defaults to 0.8, below the anchor's 1.0. Version-history folders, node_modules, dotfiles and virtual environments are skipped automatically. One /brain-index then walks every configured repo, so changes anywhere are picked up in one command.

status reports document and card counts per source, how many cards have vectors, how large the graph is, and how many cards are still waiting for enrichment — the numbers along the top of this page.

The wiring underneath

How Claude reaches the engine

The engine is an MCP server — a small program Claude Code launches at session start and talks to over standard input and output. It exposes the seventeen tools named throughout this page. Because it only loads at session start, installing or updating the plugin needs a restart before the commands appear.

Three pieces of configuration are handed to it: which project it is anchored to, which embedding model to use, and which port this dashboard should prefer.

This page

It runs on a background thread inside the MCP process, so it lives and dies with the session — no stray process to supervise. It binds to 127.0.0.1 only, tries port 4717 then the next twenty then any free one, checks the Host header on every request so a web page you visit cannot reach it by DNS rebinding, serves an explicit list of files rather than joining request paths onto a directory, and has no write routes at all. That is why it is read-only: questions go through /brain-ask, not through here.

What never leaves the machine

  • The embedding model runs locally — no API key, no inference request, no upload.
  • Entity extraction runs as subagents in your own Claude Code session.
  • The index lives inside your repo and is gitignored by default.
  • This dashboard is loopback-only and read-only.

The order you run them in

/brain-setup once, ever. Then /brain-index, and search already works. Then /brain-enrich until the queue empties, merge_entities, and /brain-enrich --communities. After that, /brain-index whenever files change — seconds — and /brain-dream now and then.

Why 512 and not 8192. bge-m3 accepts sequences up to 8192 tokens, and leaving it there is the obvious default. It also pads every 240-word card to that length, which stalls on Apple's Metal backend. The cap is the fix, and both it and the model name are overridable by environment variable.

Glossary

chunk
A ~240-word slice of a document, cut at headings, overlapping its neighbours by 36 words, remembering its file, heading and starting line.
fingerprint (sha)
A short hash of exact text. Used to decide whether anything actually changed, so expensive work is never repeated.
embedding
A passage turned into 1024 numbers positioned so similar meanings sit close together. Comparing two is one multiplication.
FTS5 / BM25
SQLite's full-text index, and the classic formula for scoring a keyword match — rare words count for more, and a long document is not rewarded for repetition.
reciprocal rank fusion
Merging rankings by position rather than score, so incompatible scales cannot be compared unfairly.
personalised PageRank
Score released at chosen starting nodes and allowed to flow through the network, with some leaking back each round. Measures “well connected to what I asked about”.
Leiden
An algorithm that finds groups in a network that are much more connected internally than externally.
entity
A person, organisation, product, place, concept, event or decision, stored once under a normalised key with every spelling kept as an alias.
functional predicate
A fact that can hold only one value at a time — owner, status, role, stage. Two open values is a contradiction worth reporting.
anchor source
The repository the plugin was installed into. Trust weight 1.0, and where captured notes land.
MCP server
The engine process Claude Code launches at session start and talks to over standard input and output.
